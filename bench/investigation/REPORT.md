# CacheLib gRPC server: implementation and comparative investigation

**Archived pre-build-fix snapshot.** This report records the first
investigation before the 1.8.0 dependency-fetch repair. The subsequent
[September 23 candidate qualification](../strong/REPORT.md) built and measured
a distinct local candidate. The [1.8.0 release qualification](../strong/RELEASE-1.8.0.md)
records the later release campaign. Statements below about 1.8.0 being unbuilt
describe this earlier checkpoint, not the final state of the repository.

Investigation date: 2026-09-23. **The checked-out 1.8.0 source was audited, but
could not be built here. Every new CacheLib performance number below is for a
separately identified 1.6.0 registry image.** This distinction matters most
for flash: that image fails to start with Navy enabled, whereas the checked-out
code contains the thread-order fix and regression tests. The present work does
not establish a measured 1.8.0 performance or SSD advantage over Redis.

## What this server implements

| Topic | Evidence in the checked-out source | Consequence |
|---|---|---|
| Cache and eviction | `CacheManager.h:150` selects `LruAllocator`; `CacheManager.cc:126-164` creates one pool with CacheLib default allocation sizes and MMLru refresh 60 s, promoting on read, not write. | This wrapper does not select TinyLFU, 2Q, or custom per-workload pools merely because CacheLib offers them. Slab class fragmentation and class-local eviction still matter. |
| RAM accounting | `CacheManager.cc:91-112` sizes hash buckets from cache size/256, clamped to 2^16–2^25, with up to 2^10 hash locks. `CacheManager.cc:898-915` reports pool usable/used bytes. | `Stats.used_size` excludes the process's hash table, gRPC/folly state, allocator overhead, and OS page cache. Container `memory.current` is the relevant real RAM budget. The published 1.6.0 binary predates dynamic hash sizing, so its measured overhead must not be assigned to 1.8.0. |
| Flash configuration | `CacheManager.cc:180-236` uses a truncate-on-start Navy file, 4 KiB blocks, 1 MiB maximum device write, 32 reader and 32 writer threads by default (the harness requests four each), 10% BigHash for ≤2 KiB, 4 KiB BigHash buckets and 8-byte filters, and 16 MiB checksummed BlockCache regions for larger items. Random admission probability is 1.0. | There is no frequency-aware admission configured here. CacheLib handles DRAM eviction to Navy and read promotion; the wrapper adds no custom policy. The current Dockerfile deliberately excludes liburing (`Dockerfile:109-112`); no io_uring capability was proven for the older tested image. The file path can be backed by many storage types; a flag alone is not proof of physical SSD. |
| Flash observability | `CacheManager.cc:922-947` sets `nvm_enabled` from the request flag and maps `navy_device_bytes_written` to `nvm_used`. | `nvm_used` is cumulative device bytes written, **not occupied SSD bytes**. With an empty NVM path, startup skips configuration (`CacheManager.cc:139`) yet `nvm_enabled` can still say true. Actual flash hits and reads require counter and correct-value proof. |
| GET/SET copies | `CacheManager.cc:252-302` copies CacheLib item memory into a new `std::string`; `CacheServiceImpl.cc:46-49` copies that into protobuf. `CacheManager.cc:303-344` allocates then `memcpy`s the decoded SET bytes into the item. | The full-object gRPC request/response also incurs protobuf parsing/serialization and transport buffers. This is not CacheLib's in-process zero-copy performance. |
| API | `proto/cache.proto:30-130` exposes 19 RPCs: key/value, batch, counter/CAS, TTL, scan, stats, health, flush, and Pipeline. `CacheManager.cc:384-417` implements batch methods as sequential loops. | No structured CacheLib items, per-pool controls, explicit admission hints, warm restart, replication, sharding, or origin integration are exposed. |
| Pipeline | `CacheServiceImpl.cc:511-589` calls `Read`, executes one operation, and calls `Write` in a loop. Only Get/Set/Delete/Exists are accepted, with an echoed sequence ID and in-band error string. | Operations are ordered and sequential **within each stream**. Concurrent gRPC streams may run on separate server threads. This is a cache request/response stream, not pub/sub, media frames, playback, or multicast. |
| Limits | `server.cc:171-173` sets both gRPC whole-message limits to `--max_item_size + 1024` (default 4,195,328 serialized bytes); `CacheManager.cc:313-344` checks value size then CacheLib's slab must also accommodate its 32-byte item header and key. The wrapper rejects empty unary keys but does not explicitly enforce a nonempty key maximum (`CacheServiceImpl.cc:31-81`). | Protobuf says 250-byte keys are recommended, not a server guarantee. A default CacheLib key above 255 bytes failed in the historical image. Whole MultiSet/MultiGet messages can be rejected with `RESOURCE_EXHAUSTED` even when each item fits. Raising the gRPC limit does not raise CacheLib's default 4 MiB slab ceiling. |
| Semantics | `CacheManager.cc:303-364` replaces an existing item and deletes via CacheLib. `CacheServiceImpl.cc:92-116` reports Delete success even for an absent key. `CacheManager.cc:674-740` handles TTL/Touch by lookup and re-SET. `CacheServiceImpl.cc:186-213` drops empty-key MultiSet entries without counting them as failures. | A miss is a successful RPC with `found=false`, not an exception. Negative/zero SET TTL becomes no expiry; positive `int64` TTL is cast to `uint32` without a range check. Touch copies/reinserts the whole value. MultiSet is neither atomic nor a guarantee that every input was attempted. |
| Flash-only edge cases | `CacheManager.cc:812-870` and `CacheServiceImpl.cc:685-716` walk only DRAM for Scan/Flush; `README.md:175-188` documents the caveat. CacheLib remove reports DRAM residency rather than flash existence. | `Flush(include_nvm=true)` is ignored and does not flush flash-only keys. Delete may remove such a key while returning `key_existed=false`. Scan is best-effort, restarts from a key cursor, and can skip entries after concurrent removal. |
| Threading and security | `server.cc:159-173` registers a synchronous gRPC service with insecure credentials and no worker tuning. `CacheManager.cc:257-350` uses sequentially consistent global counters; `CacheManager.cc:433,466,559,621,714` takes one mutex for atomic operations. `SECURITY.md` confirms no auth, ACL, or TLS. | Under contention, counter operations can serialize; all requests pay for some atomic counting. TLS/auth sidecars would add cost and need to be included in any secure comparison. Any reachable client can call Flush. |

CacheLib supports other capabilities upstream, including warm restarts,
structured items, dynamic resource management, and more policies. Their
presence in [CacheLib documentation](https://cachelib.org/docs/Cache_Library_User_Guides/About_CacheLib/)
does not make them server features. This wrapper has no durable recording store,
replication, automatic failover, cluster manager, sharding, or distributed
consistency. Its flash file is a cache tier, not a durability contract; it is
truncated on initialization.

**Measured boundary check, historical 1.6.0 image:** 250- and 255-byte keys
round-tripped; 256- and 512-byte keys were rejected. A 4,193,000-byte value
round-tripped; 4,194,303- and 4,194,305-byte values were rejected by the
service/allocator, and a 4,196,000-byte unary request hit gRPC
`RESOURCE_EXHAUSTED`. Two individually valid values in one MultiSet, and a
MultiGet returning them together, exceeded the whole-message budget and
failed with `RESOURCE_EXHAUSTED`. These probes bound observed behavior, not
an exact maximal value for every key length or the unbuilt 1.8.0 image. The
correctness runs verified binary round trips, misses, overwrite, deletion,
batch results, and Pipeline sequence IDs. A requested 1-second TTL sometimes
remained present after 1.2 seconds on 1.6.0; the bounded polling verifier
recorded actual expiry times (for example 1.79 seconds in a focused run).
Callers should not assume millisecond-precise expiry.

## Hypotheses and measurement method

The support/rejection criteria for H1–H5 were written before the full matrix
in `HYPOTHESES.md`. The new suite consists of `Dockerfile.client`,
`client.py`, `run_matrix.py`, `http_service.py`, `http_client.py`,
`run_http.py`, `run_limits.py`, `summarize.py`, and `summarize_http.py`. It reuses one client
connection per worker, uses native Python gRPC C core / redis-py / pymemcache
libraries, and validates binary values, misses, TTL expiry, overwrite, delete,
MultiGet/MultiSet, and Pipeline sequence correlation before timed runs.

The host was an Apple M2 Max MacBook Pro, 12 host cores, 32 GB RAM, macOS
26.6.2. Docker Desktop provided 8 aarch64 Linux 6.12.76-linuxkit vCPUs,
29,381,500,928 bytes of VM RAM, and overlay2. The regular matrix allowed
4 server vCPUs, 2 client vCPUs, 768 MiB container RAM per service, and
configured 96 MiB cache RAM. NVM/extstore cases additionally received a
512 MiB bind-mounted file on Docker Desktop's virtualized host storage. The
repository is on a host APFS data volume backed by internal solid-state
storage, but Docker Desktop's Linux VM and filesystem cache sit between the
containers and that device.
No host ports, raw devices, public listener, persistence, replication,
compression, or TLS were enabled. The Python client and local Docker network
are part of every end-to-end timing. Later focused cases pin server CPUs
0–3 and client CPUs 4–5; the initial broad matrix used CPU quotas without
pinning, so small throughput differences should not be interpreted as engine
differences. Exact image IDs, Docker commands, and per-case parameters are
saved with every raw run.

An operation is one object GET, except mixed traffic has one SET per ten
operations and origin mode also performs a SET on each miss. A batch is one
MultiGet, Memcached multi-get, Redis pipeline group, or short gRPC Pipeline
stream, with 16 object operations. `ops/s` counts successful object operations;
payload MiB/s counts bytes returned by successful cache GETs. Origin mode
uses fixed-size values within each case, so its object and byte hit ratios
are equal; the raw result stores both hit counts and hit bytes. Origin mode
uses a deterministic binary object and **simulates** a 5 ms backing-source
service time with `sleep` on each cache miss. Origin requests and bytes
avoided are measured events and calculated fixed-size bytes within that model,
not observed WAN traffic or financial savings. Separate HTTP tests have an
actual local origin process with the same 5 ms assumed service delay.

Each run uses a new service container. Fill/warmup is excluded from measured
time; `result.json` records its length, and the returned payload is checked
byte-for-byte. Traces have fixed seed 20260923 and use uniform, beta-skewed,
shifting hot-set, repeated, or one-pass selection. Key space, value bytes,
TTL 0 during timing, and trace generator are identical across cache backends.
The first cold-origin pass includes compulsory misses; a separately prefilled
steady-state run tests capacity after warmup. `Stats` and cgroup counters are
captured around measurement. The cgroup CPU delta is server CPU time per
object operation; the summary also divides it by wall time to show average
server CPU cores used. `memory.current` includes more than CacheLib's pool and
may include file page cache; it is sampled at the end, not a high-water mark.

**Measurement limits:** the Python trace generator can cap small-object QPS,
especially at eight threads, so these numbers are low-load/end-to-end client
observations, not maximum native-server throughput. Client CPU was not sampled
at the same granularity. p99.9 is omitted when fewer than 10,000 samples are
available. Several high-cost cases have only one run; the duplicated 1 KiB,
cold-origin, and preloaded steady-state cases preserve their variability in raw
files. Docker Desktop's
virtual disk, bind mounts, and page cache prevent conclusions about physical
SSD latency, IOPS, utilization, or NAND write amplification. The cgroup
`io.stat` deltas were zero even when extstore's own counters proved reads and
writes, so that cgroup value is not treated as device telemetry.

summary has 85 successful rows from the broad matrix and corrected reruns;
the failed verification, extstore startup, and NVM attempts remain in their

operation errors after correctness checks.

For the c1 1 KiB pair, the observed gRPC throughput was 6,708–6,797
objects/s and Redis 15,144–15,389; the observed gap is much larger than this
two-run spread. A later CPU-pinned two-run repeat widened the ranges to
6,658–8,027 gRPC and 12,506–16,688 Redis objects/s but did not reverse the
ordering. One pinned 256 KiB repeat yielded 3,316 gRPC, 5,367 Redis,
5,486 Valkey, and 6,694 Memcached objects/s, preserving the broad-run
ordering. These are validation runs, not pooled with the original matrix
median. The 8-worker gRPC result exceeded Redis/Valkey in one run but
did not exceed Memcached and is susceptible to Python scheduling and client
bottlenecks. It is **not a credible general gRPC win**. The 16-object gRPC
MultiGet row used one RPC per batch; Redis used a pipeline and Memcached
multi-get. In contrast, the gRPC `Pipeline` test opened short 16-operation
streams and achieved 6,214 objects/s, worse than its unary result. The code's
sequential handling and stream setup are plausible contributors; this test
does not characterize a sustained stream or isolate the cause. Redis and
Memcached also benefit from batched native interfaces, so H4 is only supported
relative to this server's unary mode, not relative to alternatives.

The remaining single-run size and mix probes point the same way: for 100 B
RAM hits, gRPC achieved 7,561 versus Redis 15,194 and Memcached 19,725
objects/s; for 16 KiB, 5,584 versus 12,342 and 20,673; for 64 KiB, 4,990
versus 10,232 and 11,031. A 90% read/10% write 1 KiB trace yielded 6,556
gRPC, 15,384 Redis, and 24,469 Memcached operations/s. At the separately
probed 4,193,000-byte value near the default gRPC limit, gRPC yielded 234,
Redis 331, and Memcached 446 objects/s in just 20 requests; that tiny sample
is a boundary/correctness probe, not a stable large-object throughput claim.
Per-run payload MiB/s and p50/p95/p99 appear in the CSV. These traces were
RAM-hit or mixed cache-service tests, not video playback.

**Capacity and real memory.** The logical uniform working set is 2,048 ×
64 KiB = 128 MiB of reusable payload; the first 200 accesses in cold runs
form the warmup, while the prefilled run loads the full keyspace and then does
1,000 excluded warmup operations. In the cold run, gRPC's 1,684/3,300 hit
ratio (51.0%) marginally exceeds Redis's 48.5%, but gRPC consumed 230.6 MiB
of cgroup memory at the end against Redis 94.1 MiB, Valkey 92.6 MiB, and
Memcached 100.0 MiB. The tested old image's fixed, large hash table is a
likely source of that overhead; current 1.8.0 source sizes it dynamically,
which remains unmeasured. Under a **common 256 MiB container cap**, with
gRPC still configured for 96 MiB cache and the other RAM engines configured
for 192 MiB, gRPC retained 1,684 hits while Redis, Valkey, and Memcached each
retained 1,805 and needed only the 1,495 compulsory origin reads. This is a
resource-budget comparison, not identical configured-cache capacity; actual
end memory was 230.7, 138.4, 128.9, and 119.6 MiB, respectively. It
contradicts a claim that this measured gRPC build uses less RAM for useful
content. `Stats.used_size` would hide the process overhead, so all memory
claims here use cgroups. Useful logical payload bytes can be recovered from
the fixed-size object counts; neither `used_size` nor extstore's logical
`bytes` is a physical-memory measure.

**Flash proof and origin value.** The 1.6.0 gRPC image exited at startup with
NVM enabled: `number of read/write threads should be set first as non-zero
value`. No CacheLib SSD hit, SSD benefit, or H2 result was measured. The
checked-out 1.8.0 source puts the Navy thread setup before async I/O, but
build failure prevented a test. Memcached extstore *did* demonstrate the
hybrid mechanism on identical 96 MiB configured RAM plus a **reported extra
512 MiB file**. In the paired prefilled runs it retained 3,662–3,663 of
4,000 objects versus RAM-only Memcached's 2,782, avoiding about 880 further
5 ms simulated-origin requests and 55 MiB of origin payload per run. Its
Memcached counters in one run increased by 1,034 flash-object reads and
22.25 MB flash-object writes during measurement; the binary GET verifier
checked returned bytes. This supports H2/H3 for an accessible *alternative*,
not for the current CacheLib wrapper. The 1,164 versus 423 objects/s rate is
mostly explained within this model by fewer origin sleeps; it is not evidence
that an SSD hit is faster than a RAM hit. Its end cgroup memory was 108.5 MiB
versus 100.1 MiB for RAM-only Memcached, with extra file capacity and
unquantified Docker VM page-cache memory. Write counters measure logical
extstore traffic, **not NAND write amplification**. No physical disk reads,
IOPS, saturation, or endurance were established.

**Changing and one-pass access.** The shifting-hot-set 64 KiB trace yielded
3,016/3,300 hits (91.4%) for every backend: it did not create a useful
capacity separation. A one-pass 64 KiB trace produced **zero hits** and
450 origin requests in 450 measured cache requests. The gRPC path delivered
117 objects/s and p50 8.52 ms, while a bypass-only simulated-origin run
delivered 150 objects/s and p50 6.82 ms. The bypass run has 500 measured
operations versus 450 after cache warmup, so the difference is directional
rather than a tightly matched overhead estimate. With no reuse, every cache
SET added work and avoided no origin requests. This supports H5's negative
case and cautions against indiscriminate caching of fresh segments.

**Hypothesis disposition.** H1 is supported only as a measurable end-to-end
difference: this old gRPC service was slower for single-worker 1 KiB and
256 KiB/1 MiB RAM hits, with higher server CPU time per operation (for paired
1 KiB, 118 µs gRPC versus 30 Redis and 23 Memcached). Average server CPU
use was .795 gRPC, .457 Redis, .449 Valkey, and .397 Memcached cores of the
four-core allowance. The test does not isolate CacheLib's engine from gRPC,
client libraries, allocator sizing, or copies. H2 for this wrapper is **not
validated**; the historical image is
contradicted by startup failure. H3 is demonstrated conditionally in the
simulated-origin extstore case, not in this server. H4 shows gRPC MultiGet
improves object rate over its unary call and is outpaced by competent native
batching in this test. H5 is supported by repeated-object hits and the
zero-hit one-pass case. Tail p99 in miss-heavy rows mixes cache hits and
the assumed origin delay; it should not be read as isolated cache tail latency.

Raw distribution samples, errors, throughput in MiB/s, p50/p95/p99,
per-run CPU and memory snapshots, origin requests/bytes, extstore counters,
and SVG charts are in the JSON/CSV artifacts. Sample counts are too small
for defensible p99.9 reporting. No engine-only benchmark or detailed CPU
profile was obtained; the direct code-copy audit gives a plausible mechanism,
not an attribution of measured time.

## Media-object applicability

This is a **media-object cache** experiment, never a playback or live-stream
test. The common HTTP comparison puts NGINX's disk proxy cache and a Python
HTTP→gRPC adapter in front of a local origin whose response takes a declared
5 ms. The two paths return byte-identical 256 KiB or 1 MiB binary objects.
NGINX's files are on a Docker Desktop bind mount and likely page-cached;
calling these physical SSD hits would be unjustified. The Python adapter's
HTTP parsing, cache lookup, and whole-object copies are included in its rate.
The common interface improves delivery comparability, but does not isolate
NGINX from adapter overhead. The adapter and origin code and exact commands
are retained in `run_http.py` and the HTTP run directories. The table uses
two equal-budget runs (`2026-09-23-http-equal-1.6` and `...-repeat-1.6`):
NGINX had 2 CPU/768 MiB, while the Python adapter and gRPC container each
had 1 CPU/384 MiB, sharing CPUs 0–1. The client used CPUs 4–5 and the origin
6–7. Both paths returned the **entire verified body**. The earlier
`2026-09-23-http-1.6` run is preserved with a weaker prefix/length check;
`2026-09-23-http-fullcheck-1.6` tightened that check before equalizing the
cache-path resource allowances.

| Repeated 256 KiB, one reader: requests/s range; p50 ms range | 2,441–2,538; .355–.372 | 1,976–2,029; .431–.444 | 0 / 0 |
| Repeated 256 KiB, eight readers: requests/s range | 2,631–2,785 | 2,708–3,026 | 0 / 0 |

Generated views: [repeated 256 KiB](runs/2026-09-23-http-equal-1.6/chart-repeated-262144-1.svg),
[repeated 1 MiB](runs/2026-09-23-http-equal-1.6/chart-repeated-1048576-1.svg), and
[charged cache-path memory](runs/2026-09-23-http-equal-1.6/chart-repeated-256k-memory.svg).

The two short runs favor NGINX for one-reader repeated objects and the
one-pass path. The eight-reader ranges overlap and their ordering reversed;
that case is inconclusive and may approach the Python client limit. The
earlier full-body run also favored NGINX at one reader (2,804 versus 1,710
requests/s for 256 KiB). In the equal-budget 256 KiB runs, summed cgroup
memory for the adapter and gRPC containers was 190–191 MiB; NGINX's own
cgroup showed about 4.5 MiB, **but its bind-mounted file/page cache is not
fully charged there**, so this is not a complete system-memory comparison.
NGINX's cache created 247 files totaling about 86 MiB on its bind mount over
the first HTTP test. No physical I/O attribution was possible.
Both systems can avoid origin traffic for repeat readers, recent replay,
seeking to cached **objects**, course/podcast/concert segments, thumbnails,
previews, manifests, metadata, and reusable text-to-speech output. This
server requires application code to choose keys, segment boundaries, TTL,
fill, eviction response, HTTP/range handling, authorization, and origin
fallback. Its ~4 MiB default whole-RPC limit and whole-object copies make
large unchunked media a poor direct fit; chunking would be application
semantics, and was not secretly applied to just one comparator.

A fresh one-pass stream may cost more to admit than it saves. The gRPC
`Pipeline` RPC is sequential request/response cache access, not broadcast or
publish/subscribe. A cache is neither a playback/jitter buffer nor a durable
recording store, media server, or streaming transport. There is no timeline,
multi-viewer distribution, adaptive bitrate, synchronization, packet-loss
recovery, or player behavior here. No viewer startup time, dropped frames,
audio continuity, or playback quality was measured. An HTTP cache such as
NGINX is already closer to the delivery interface for encoded segments.

## Prioritized engineering work

1. Make a reproducible 1.8.0 build: vendor or mirror the failing pinned gRPC
   submodules, record resolved CacheLib/Folly/fbthrift hashes and immutable
   image digest, then run `NvmHybridTest` and this suite in CI. This blocks
   every current-version performance and hybrid claim.
2. Prove current-version Navy on file-backed storage: require correct binary
   flash reads and rising NVM hit/read/write counters under a constrained
   DRAM trace. Publish actual DRAM/flash occupancy, eviction, admission, and
   device I/O metrics; measure on a controlled physical SSD before claiming
   latency or endurance. The old image failed startup and existing `nvm_used`
   is mislabeled cumulative traffic.
3. Define/fix semantic hazards with compatibility care: key and TTL bounds,
   whole-batch size errors and per-item failures, flash-aware Delete/Flush/
   Scan behavior, `nvm_enabled` truth, and stats that distinguish pool from
   process memory. The code audit found these without needing a speed test.
4. Add a documented secure deployment path with TLS/auth or a tested proxy,
   and decide explicitly whether external sharding, replicas, health checks,
   and cache refill are required. These are practical reasons to choose Redis
   or Valkey today even if a future CacheLib workload wins on hit ratio.
5. Only after a representative profile, reduce GET/SET whole-object copies
   and test sustained Pipeline streams, worker tuning, and admission policy.
   The observed small-object and media-object gaps justify investigation but
   do not prove which internal stage dominates.
6. For media, benchmark the complete HTTP/range/segment path under a measured
   origin and multiple readers. Retain NGINX as a baseline and prefer it when
   standard HTTP caching meets the objective; keep live transport and durable
   recording outside this cache service.

| Evidence label | Important conclusion |
|---|---|
| **Measured in this repository** | The historical 1.6.0 gRPC image lost to Redis, Valkey, and Memcached on c1 1 KiB and 256 KiB RAM hits; it used substantially more cgroup memory at 96 MiB configured cache. CPU-pinned repetitions preserved the ordering. |

| **Supported by implementation inspection** | The current wrapper selects LruAllocator/MMLru, copies whole GET/SET values, processes operations sequentially within a Pipeline stream, exposes no pub/sub/media transport, and supplies no TLS/auth or distributed recovery. |

| **Hypothesis not yet validated** | A successfully built 1.8.0 image might gain reusable-content capacity or better real-memory efficiency through Navy and dynamic hash sizing; no current-version result exists. Physical SSD latency and endurance are likewise unmeasured. |
| **Unsupported or contradicted** | Claims that this service already beats Redis generally, uses less real RAM in the measured setup, provides live media delivery, or that its historical `Ping`/`Get` ratio identifies a precise gRPC bottleneck. |

> Nakitte financial-content workload, where news and other content are
> requested repeatedly and RAM use matters. My contribution was the service
> integration: API and binary semantics, CacheLib configuration, Docker build,

**Direct answers.** The measured 1.6.0 service has no robust general
performance or RAM-efficiency advantage over Redis, Valkey, or Memcached in
these tests; one eight-worker Redis/Valkey comparison favors gRPC but has one
run and a client bottleneck risk. There is no measured CacheLib SSD advantage.
The strongest unmeasured architectural possibility is a working, tuned Navy
tier retaining more reused objects under constrained RAM, as the extstore
control illustrates for a different engine. Redis/Valkey are preferable for
their mature secure and distributed operation, Memcached for the simple,
fast ephemeral KV workload observed here, extstore for tested flash capacity,
and NGINX for HTTP media caching. This project can be a component for
reusable media **objects** with surrounding delivery software. It is not a
complete live-streaming platform. Its strongest honest value is a concrete
CacheLib service integration and reproducible evaluation of the tradeoff
against ready-made caches, originating in repeated financial-content access
and RAM/SSD exploration.
